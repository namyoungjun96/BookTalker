DB 순서와 배치 / 조회 책임 분리

배치 통합 테스트를 Top10 컷·장르 분리까지 마무리하면서, "정렬해서 저장하면 그 순서로 나온다"는 잘못된 가정을 바로잡았다. DB가 순서를 보장하지 않는다는 사실에서 출발해, 배치와 조회의 책임이 어떻게 갈리는지 정리한다.

이번 세션 · 완료
  • 쿼리 단 마무리 — 회독수(규칙 A) / 리뷰 3개 경계(규칙 B)
  • 한 장르 Top10 컷 테스트 — 11권 중 제일 낮은 1권이 빠졌나(noneMatch)
  • 장르 분리 테스트 — 장르별로 각각 집계, 점수 갈라 "전체 자르기 버그" 드러나게
  • DB 순서 보장 / 배치·조회 책임 분리 개념 정리
  • m=3에선 shrinkage가 약하다 — 역전이 잘 안 나는 걸 계산으로 발견
01

DB는 순서를 보장하지 않는다

"정렬해서 저장하면 그 순서로 나온다"는 RDB에서 성립하지 않는다

관계형 DB는 ORDER BY 없이 SELECT하면 행 순서를 보장하지 않는다. 저장 순서대로 나올 때도 있지만 보장이 아니라, 그걸 믿고 짜면 언젠가 깨진다. 순서가 필요하면 무조건 조회 시 ORDER BY.

그럼 배치의 sorted()는?

저장 순서가 아니라 Top10을 자르기 위한 것

배치의 sorted(weightedScore 내림차순)은 바로 뒤 limit(10)이 "상위 10개"를 자르도록 하는 전제다. 정렬 안 하고 자르면 "아무 10개"가 된다. 자르고 나면 그 정렬이 DB에 유지되든 말든 상관없다 — 보여줄 순서는 조회가 책임지니까.

테스트 함의
그래서 배치 테스트에서 findAll()의 순서로 "정렬됐나"를 검증하려던 접근이 틀렸다. 배치 테스트는 "올바른 집합을 골랐나"(어떤 10개)를 보고, 순서 검증은 조회 테스트(ORDER BY)의 몫이다. "검증할 때 정렬 자체에 신경 쓰지 않는다."
02

배치와 조회의 책임

무엇을 미리 해두고(배치), 무엇을 매번 하나(조회)

배치 (하루 한 번)

Top10 깎기 — 조회 때마다 깎으면 낭비. 미리 잘라 저장.

가중 평점 계산, 정렬(자르기용), 장르별 그룹핑, 저장.

조회 (매 요청)

정렬해서 보여주기 — ORDER BY. DB가 인덱스로 싸게 한다.

이미 잘려 저장된 걸 장르 필터 + 정렬해 읽기만.

핵심 구분: 깎기(Top10)는 비싸니 배치로, 정렬은 DB가 싸게 하니 조회로. 기존 getRankByGenre가 문제였던 건 "조회 때마다 자바에서 groupingBy하고 limit으로 깎는 곡예" 때문이지, 정렬 자체가 문제는 아니었다. 깎기를 배치로 옮기면 조회는 단순 쿼리(ORDER BY weighted_score DESC) 하나로 끝난다.

03

장르 분리 테스트 설계

"전체에서 자르기" 버그가 드러나게 점수를 가른다

장르별로 각각 Top10이 되는지 보려면, "전체에서 자르기" 버그가 있을 때 한 장르가 통째로 밀려나야 한다. 그래야 그 버그가 테스트로 드러난다.

✗ 점수 비슷하게

소설·에세이 점수가 엇비슷하면, 전체 자르기 버그가 있어도 둘이 섞여서 상위 10에 들어간다. 에세이가 일부 살아남아 버그를 못 잡는다.

✓ 점수 확실히 가르기

소설 11권 높게(5) + 에세이 3권 낮게(1). 전체 자르기면 상위 10이 소설로 꽉 차 에세이가 0권 → 실패로 잡힌다. 정상이면 장르별로 각각 살아남아 통과.

필터 후 검증의 함정
filter(genre=="소설")로 거른 novel 리스트에 noneMatch(genre=="에세이")를 거는 건 무의미 — 이미 소설만 걸렀으니 항상 통과한다. "섞임"은 개수 검증(소설 10, 에세이 3)이 이미 잡는다. 섞였으면 개수가 어긋나니까.
04

m=3에선 역전이 잘 안 난다

정렬 테스트 데이터를 설계하다 직접 계산으로 발견한 것

가중 평점 식 (v/(v+m))R + (m/(v+m))C에서 m은 "전체 평균 C에게 주는 가상의 표 개수"다. m이 작으면 C의 발언권이 약해 shrinkage가 약하다. m=3이면 리뷰 3개인 책도 자기 평점과 C를 정확히 반반 섞어 — 자기 평점이 절반은 살아남는다.

그래서 "리뷰 적고 평점 높은 책"이 "리뷰 많고 평점 낮은 책"에게 순위가 역전되는 일이 m=3에선 거의 안 일어난다. 리뷰 3개·5.0 vs 30개·4.0을 계산해도 5.0짜리가 이긴다. m을 키우면 역전이 잘 나지만 — 데이터가 적은 현재는 모든 책이 평균으로 수렴해 변별력을 잃으므로 지금은 m=3 유지, 데이터 쌓이면 조정이 맞다.

"테스트 통과시키려고 m을 바꾸기"(본말전도)와 "지표가 취지에 안 맞아 m을 재검토하기"(도메인이 정책을 정함)는 정반대다. 후자는 정당한 판단이다. 정렬 테스트는 역전 욕심을 버리고 "가중 평점 순으로 저장되나"만 보고, shrinkage 작동은 계산기 단위 테스트가 이미 증명한다.

06

다음 · 조회 단 정리

배치가 다 해뒀으니, 조회의 곡예를 단순 쿼리로 걷어낸다

  • getRankByGenre 고치기 — findAllGroupable + 자바 groupingBy + limit(10) 곡예를 제거배치가 이미 장르별 Top10을 저장하므로 조회는 ORDER BY 단순 쿼리로 충분 · 장르별 저장이 테스트로 확인됐으니 이제 안전하게 교체
  • 미사용 getRank 제거 — 호출처 없는 죽은 코드정렬도 AvgRating 기준이라 어차피 낡음
  • (선택) weightedScore 값 정확성 — 통합에서 또 볼지계산기 단위 테스트가 사실상 커버 중 · 중복이면 생략 가능
현재 손에 있는 것
배치 본체 구현 완료 · 쿼리 단 테스트(리뷰3개·회독수) · 계산 단(가중평점·C·예외) · 배치 통합(가드·생성·Top10컷·장르분리). 남은 건 조회 단 정리뿐 — 배치가 무겁게 다 해놨으니 조회는 가벼워진다.
