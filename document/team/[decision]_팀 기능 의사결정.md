## API 명세 (2026-10-07)

3. 이미 있는 명세서에 코드를 맞춤 -> 명세를 기준으로 삼아야 이후 API에도 같은 기준을 적용할 수 있음
4. 입력값 검증은 Bean Validation(`@Valid`) 사용 -> 제약이 DTO에 모여 있어 명세서와 대조하기 쉬움
5. 모임 생성 후 응답 body의 `teamId`로 상세 페이지 이동, `Location` 헤더는 사용 안 함 -> CORS에서 `Access-Control-Expose-Headers` 설정이 따로 필요해서
6. 피드 페이지는 `?page=` 쿼리, 1부터 시작, 0 이하는 첫 페이지, 4개 고정 -> 화면 번호와 일치, Spring `one-indexed-parameters` 설정 활용
7. 피드 응답에 `totalPages` 추가 -> 프론트가 페이지 버튼을 그리기 쉬움, Spring `Page`를 그대로 노출하지 않음(내부 필드 노출 방지)
8. 피드 정렬은 수정일 최신순, 같으면 reviewId 내림차순 -> 최신 글이 위로
9. 피드에 가입 전 리뷰도 포함, INACTIVE·BANNED 사용자의 리뷰는 제외 -> 정의서의 "전체공개/모임공개 독후감은 속한 모든 모임에 공개"와 일치, 쿼리도 단순

## 권한과 예외 (2026-10-07)

10. ⭐ 팀 없음과 모임원 아님을 구분하지 않고 둘 다 404로 위장 -> 모임 존재 여부를 드러내지 않기 위해
    - 둘을 다르게 응답하면, 외부에서 teamId를 하나씩 넣어보며 "이 번호의 모임이 존재하는지"를 알아낼 수 있음
    - 그래서 팀 존재 확인을 따로 하지 않고, "ACTIVE 모임원 조회" 하나로 두 경우를 같은 경로에서 처리
    - 반면 모임원인데 모임장이 아닌 경우는 403 -> 이 사용자는 이미 모임이 있다는 걸 알기 때문에 숨길 것이 없음
11. INACTIVE·BANNED 사용자도 모임원이 아닌 것으로 보고 404 -> 탈퇴·추방된 사용자는 모임원이 아님
12. 피드 접근 권한도 403이 아니라 404 -> 수정·삭제와 정책 통일
13. ⭐ 검증 오류 메시지는 어노테이션 message에 필드 이름을 포함, 첫 번째 오류 하나만 응답 -> 프론트가 토스트에 그대로 표시 가능
    - `e.getMessage()`를 그대로 응답하면 내부 클래스명과 사용자 입력값이 노출됨 -> 로그에만 남김
    - 핸들러에서 필드명을 붙이는 방식은 Java 필드명(`teamName`)이 사용자에게 보여서 선택하지 않음
14. `ResponseEntityExceptionHandler` 상속은 예외 처리 리팩토링 때 진행 -> 상속하면 Spring 기본 예외 응답이 ProblemDetail 형태로 바뀌어 프론트 영향이 큼
15. 예외 메시지의 `[메서드명]` 태그는 지금은 유지 -> 일관성 유지, 로그용·응답용 메시지 분리는 리팩토링 때

## 구현 (2026-10-07)

16. ⭐ 수정·삭제에서 팀은 조회한 모임원에서 가져옴(`member.getTeam()`) -> 추가 쿼리가 없고 `getReferenceById`의 늦은 예외 문제가 없음
    - `getReferenceById`는 DB 조회 없이 프록시만 돌려줌. 팀이 없으면 그 줄이 아니라 **처음 필드에 접근할 때** `EntityNotFoundException`이 남 -> try/catch로 감싸도 못 잡음
    - 모임원이 조회됐다면 FK 때문에 팀은 반드시 존재함 -> 팀이 사라지는 경우는 동시 삭제 같은 불변조건 위반뿐이라 500이 맞음
    - `TeamMember.team`은 `@ManyToOne` 기본값 EAGER라 모임원 조회 시 팀도 함께 로딩됨
    - `getReferenceById`는 엔티티를 읽지 않고 FK만 연결할 때 쓰는 것 (예: `saveMember`의 `member.setTeam(...)`)
