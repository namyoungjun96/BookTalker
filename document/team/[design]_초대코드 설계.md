# 1. 문제

스펙과 코드의 초대코드 모델이 다르다.

| | 스펙 정의서 | 현재 코드 |
| --- | --- | --- |
| 저장 위치 | `team.invite_code` 컬럼 (NOT NULL + UNIQUE, 13자) | `TeamInvite` 테이블 (`team_id` FK, `code` UNIQUE, `active`) |
| 발급 시점 | 모임 생성 시 함께 발급 ("코드가 항상 존재한다는 불변식을 지키기 위해 생성/발급을 분리하지 않음") | 모임장이 `createInviteCode` 호출 시. 호출할 때마다 새 활성 코드 추가 |
| 팀당 코드 수 | 1개 | N개 (활성 코드도 N개 가능) |
| 재발급·비활성화 | Non-goal | `revokeInviteCode(code)` 서비스 존재, 컨트롤러 미연결 |
| API | `GET /teams/{teamId}/code` (조회만) | 발급 API (`POST`) + 가입 API |

이 상태로는 초대코드 조회·가입 API 명세를 쓸 수 없다. "조회"가 어떤 코드를 돌려줄지(N개 중 무엇?)부터 정해지지 않기 때문이다.

# 2. 선택지

## A. `team.invite_code` 컬럼 (스펙 정의서 원안)

- 모임 생성 트랜잭션에서 코드를 만들어 `team`에 함께 저장
- 가입: `teamRepository.findByInviteCode(code)`
- 조회: 모임장이 자기 팀의 `inviteCode`를 읽음

| 장점 | 단점 |
| --- | --- |
| **"모임에는 항상 코드가 1개 있다"를 DB가 보장** (NOT NULL + UNIQUE). 코드 없는 모임, 활성 코드 N개 같은 상태가 생길 수 없음 | 코드 이력(언제 무슨 코드였는지)이 남지 않음 |
| 테이블·엔티티·연관관계·cascade 하나씩 줄어듦 → 삭제 시 FK 문제 없음 | 만료일, 코드별 사용 횟수 같은 확장은 테이블로 옮겨야 함 |
| 명세가 단순해짐: 조회 1개 + 가입 1개 | |
| 나중에 재발급이 필요하면 **컬럼 값을 덮어쓰는 것만으로 구현 가능** (이전 코드는 자동 무효) | |

## B. `TeamInvite` 테이블 (현재 코드)

| 장점 | 단점 |
| --- | --- |
| 코드 여러 개, 만료, 이력, 비활성화 등 확장에 유연 | 스펙의 Non-goal(재발급)을 위한 구조를 지금 유지해야 함 |
| 이미 구현·테스트가 있음 | "팀당 활성 코드 1개"를 지키려면 **애플리케이션 코드로** 보장해야 함 (부분 유니크 인덱스 등 추가 작업) |
| | 모임 생성 시 코드 발급을 같은 트랜잭션에 넣지 않으면 코드 없는 모임이 생김 |
| | 발급·비활성화 API, 테스트, 프론트 화면까지 범위가 커짐 |

## 비교

| 기준 | A. 컬럼 | B. 테이블 |
| --- | --- | --- |
| 스펙 일치 | ✅ 그대로 | ❌ 스펙 수정 필요 |
| 불변식 보장 | DB 제약 | 애플리케이션 코드 |
| 남은 기간(10/25 배포) 내 작업량 | 적음 (삭제 위주) | 많음 (정책 + API 추가) |
| 나중에 확장 | 재발급은 쉬움, 이력·만료는 테이블로 이전 필요 | 쉬움 |
| 되돌리기 비용 | 낮음. A → B 이전은 `team.invite_code`를 `TeamInvite`로 옮기는 INSERT 한 번 | — |

# 3. 추천: A. `team.invite_code` 컬럼

1. **지금 필요한 요구사항은 "모임당 코드 하나, 모임장만 조회"뿐이다.** B의 유연성은 전부 Non-goal(재발급, 가입 신청 등)을 위한 것이다.
2. **불변식을 DB가 지킨다.** "코드가 항상 존재한다"를 NOT NULL로 강제하면 서비스 코드에서 확인할 필요가 없다. B에서는 같은 규칙을 코드와 테스트로 계속 지켜야 한다.
3. **되돌리기 쉽다.** 실사용 테스트에서 재발급이나 만료가 필요해지면, 그때 테이블로 옮기는 비용이 크지 않다. 반대로 B를 유지하면서 생기는 정책 결정(활성 코드 수, revoke API 명세)은 지금 당장 비용이 든다.
4. **지금이 바꾸기 가장 싼 시점이다.** 팀 기능은 운영에 배포되지 않았다 (배포 전 확인 필요: 운영 DB에 `Team`/`TeamInvite` 테이블이 없는지).

면접용 한 줄: "확장성보다 지금의 불변식을 DB 제약으로 보장하는 쪽을 택했고, 확장이 필요해지면 이전 비용이 낮다는 점을 근거로 삼았다."

# 4. 재시도를 다 써도 실패할 때의 응답

## 4-1. 실제로 일어날 확률

- 62종 문자 × 13자리 = 62^13 ≈ **2 × 10^23** 가지
- 모임이 n개일 때 한 번이라도 충돌할 확률 ≈ n² / (2 × 62^13)
  - 모임 100만 개여도 약 **2.5 × 10^-12**
- 3회 연속 충돌은 사실상 일어나지 않는다. 재시도는 "보험"이고, 소진 응답은 **장애 상황**에 대한 응답이다.

## 4-2. 재시도 위치: 트랜잭션 안에서 `save` 실패를 잡으면 안 된다

`createTeam`은 `@Transactional`이다. `teamRepository.save(team)`에서 UNIQUE 위반이 나면:

- 예외가 리포지토리의 트랜잭션 프록시를 지나면서 **바깥 트랜잭션이 rollback-only로 표시**된다
- Hibernate 세션도 예외 이후 재사용할 수 없는 상태가 된다
- 그래서 catch 후 새 코드로 다시 `save`해도, 커밋 시점에 `UnexpectedRollbackException`이 난다 (`롤백온리_실험` 테스트가 확인한 동작과 같음)

선택지:

| 방식 | 설명 | 평가 |
| --- | --- | --- |
| ① 저장 전 존재 확인 | 코드 생성 → `existsByInviteCode` → 있으면 다시 생성 (최대 3회) → 저장. UNIQUE 제약은 마지막 방어선 | 트랜잭션 문제 없음. 확인과 저장 사이 경쟁은 확률상 무시 가능하고, 생겨도 UNIQUE가 막음. **추천** |
| ② 트랜잭션 밖에서 재시도 | 컨트롤러나 별도 빈에서 `createTeam` 전체를 재시도 | 스펙의 "모임 생성 전체 재시도"와 일치하지만 구조가 복잡해짐 |
| ③ 재시도 없음 | UNIQUE 제약만 두고 충돌 시 실패 | 가장 단순. 다만 `DataIntegrityViolationException`이 전역 핸들러에서 **409**로 나가서 "사용자 요청이 충돌했다"는 잘못된 의미가 됨 |

## 4-3. 소진 시 응답

| 응답 | 의미 | 평가 |
| --- | --- | --- |
| **500** | 서버가 처리하지 못함 | **추천.** 확률상 버그나 난수 생성기 이상 같은 장애이므로 서버 오류가 정확함. 기존 `Exception` 핸들러 → prod에서 Discord 알림까지 자동 |
| 503 | 일시적 과부하 | "잠시 후 다시"는 맞지만 503은 서버 가용성 문제를 뜻해서 의미가 맞지 않음 |
| 409 | 요청 충돌 | 사용자 입력과 무관한 충돌이라 부적절 |

- 사용자 안내: 프론트는 500을 "일시적인 오류, 다시 시도해 주세요"로 표시한다. 모임이 생성되지 않았으므로(롤백) 다시 눌러도 중복 생성 문제는 없다.
- 예외 타입: 지금은 별도 예외를 만들지 않고 `IllegalStateException`처럼 **400·409로 매핑되지 않는 예외**로 던지면 500이 된다. ⚠️ `IllegalArgumentException`은 400으로 매핑되니 쓰면 안 된다.

### 엔티티·리포지토리

| 대상 | 변경 |
| --- | --- |
| `Team` | `inviteCode` 필드 추가 (`nullable = false, unique = true, length = 13`), `teamInvites` 연관관계 제거 |
| `TeamInvite`, `TeamInviteRepository` | 제거 |
| `TeamRepository` | `findByInviteCode`, `existsByInviteCode` 추가 |
| `TeamMember` | (선택) 재가입용 상태 전이 메서드. 예: `rejoin(displayName)` — `status` → ACTIVE, `displayName` 교체, `joinedAt` → 현재 시각. setter를 서비스에 흩어 두지 않고 "INACTIVE일 때만 복구"라는 규칙을 엔티티 한 곳에 모으는 목적 |

### 서비스

| 대상 | 변경 |
| --- | --- |
| `createTeam` | 코드 생성 → `existsByInviteCode`로 확인, 최대 3회 재생성(4-2 ①) → `team`에 설정. 3회 모두 충돌하면 500으로 떨어지는 예외(예: `IllegalStateException`. ⚠️ `IllegalArgumentException`은 400) |
| `createInviteCode` / `revokeInviteCode` | 제거 |
| 초대코드 조회 (신규) | ACTIVE 모임원 조회(없으면 `NotFoundTeamException` 404) → OWNER 아니면 `TeamAccessDeniedException` 403 → `member.getTeam().getCode()`. 수정·삭제와 같은 패턴 |
| `joinTeamByInviteCode` | `TeamInvite` 대신 `teamRepository.findByInviteCode` (없으면 `NotFoundInviteCodeException` 404). `active` 확인 제거. 기존 행 분기: 없음 → INSERT / ACTIVE → 409 / BANNED → 404 / **INACTIVE → 기존 행 복구** (새로 추가). 반환값으로 `teamId` |
| `addMember` | 기존 행이 INACTIVE면 같은 방식으로 복구 (현재는 분기를 통과해 INSERT → 유니크 위반 409). `@Transactional` 누락도 함께 확인 |

### 컨트롤러·DTO

| 대상 | 변경 |
| --- | --- |
| 초대코드 조회 | `POST /teams/{teamId}/code` → `GET /teams/{teamId}/code`, 응답 200 + `{ code }` (응답 DTO 필요) |
| 초대코드로 가입 | `POST /teams/code` → `POST /teams/join`, `@Valid` 추가, 응답 200(body 없음) → 201 + `{ teamId }` (`CreateTeamResponse`를 재사용할지, 가입 전용 DTO를 만들지는 선택) |
| `JoinByInviteCodeRequest` | 검증 추가: `code` `@NotBlank`(형식 검증 없음), `displayName` `@NotBlank` + `@Size(max = 10)` (메시지는 `CreateTeamRequest`와 같은 형식) |

### 테스트

| 대상 | 변경 |
| --- | --- |
| 정리 | `createInviteCode_*`, `revokeInviteCode_*`, `팀_팀원_초대코드_cascade_삭제` 제거 또는 새 구조로 수정. `joinTeamByInviteCode_정상_동작`은 `createInviteCode` 대신 생성된 팀의 `inviteCode` 사용 |
| 추가 | 모임 생성 시 코드 발급 / 코드 조회: 모임장 200, 모임원 403, 비회원·INACTIVE·BANNED·없는 팀 404 / 가입: 없는 코드 404, BANNED 404, ACTIVE 409, **INACTIVE 재가입 시 같은 행이 ACTIVE로 복구되고 닉네임·joinedAt이 바뀌는지** / `addMember` INACTIVE 복구 |

### DB

- `ddl-auto: update`는 기존 `TeamInvite` 테이블을 지우지 않는다. 로컬 DB에 남은 테이블은 직접 정리
- 기존 `team` 행이 있는 DB에 NOT NULL 컬럼을 추가하면 실패한다. 로컬에 테스트 모임 데이터가 있으면 정리 후 실행. 운영 DB에 팀 테이블이 없는지 배포 전 확인

# 6. 논의 결과 (2026-10-08)

### 모델: A. `team.invite_code` 컬럼

### 발급 시점: 생성 시 자동 발급 + 재발급은 별도 행위 (중간안)

논의 과정에서 "모임 생성과 코드 발급은 다른 행위이니 API를 분리하자"는 의견이 나왔다. 행위 관점으로 다시 나눠 보면 다음과 같다.

| 행위 | 모임장의 의도 | 분류 |
| --- | --- | --- |
| 처음 발급 | 없음. 모임을 만들면 어차피 초대하므로 "만들자마자 있으면 좋은 것" | 모임의 속성 (`teamId`처럼 생성 시 함께 생김) |
| 재발급 | 있음. "유출됐으니 바꾸자" | 별도 행위 → 별도 API |
| 초대 닫기 | 실사용 모임에서 필요 없음 | 만들지 않음 |

- 완전 분리(발급 API를 따로 둠)가 자연스러우려면 `invite_code = null`이 "초대를 받지 않는 중"이라는 의미 있는 상태여야 한다. 초대 닫기가 필요 없으므로 null은 의미 없는 상태가 되고, NOT NULL 불변식만 잃는다.
- 그래서 **처음 발급은 생성에 포함하고, 재발급만 별도 행위**로 둔다.
- 충돌 확률(약 10^-12)은 분리 여부의 근거로 쓰지 않았다. 거의 일어나지 않는 상황을 위해 구조를 바꾸는 것이기 때문이다.
