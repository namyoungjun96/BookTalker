| --- | --- | --- | --- |
| M1 ✅ | `deploy.sh` 내용 | `cat /home/ubuntu/deploy.sh` → 검토용으로 공유 | 포트 전환 방식(8010/8011 교대인지, Nginx upstream 전환인지), 실패 시 동작 확인. D3·5장 수정 범위 |

# 3. 판단 기준 (개발자가 정하는 것)

D1의 답은 기술보다 **이 서비스를 어떻게 운영할지**에 달려 있다. 아래 질문에 먼저 답한다.

| # | 질문 | 이렇게 답하면 | 이렇게 답하면 |
| --- | --- | --- | --- |
| Q1 | 배포 중 **1~2분 접속 불가**를 허용할 수 있나? | "허용" — 지인 모임이고, 배포는 main 머지 시점을 내가 고를 수 있다(사람 적은 시간대) → **②가 유력** | "허용 못 함" — 독후감 작성 중 저장이 실패하면 글이 날아갈 수 있다 → **①** |
| Q2 | 실사용 중 배포를 얼마나 자주 할까? | 주 1~2회 → 다운타임 누적이 작음 → ②도 무방 | 피드백 반영으로 하루 여러 번 → 다운타임이 사용자에게 자주 보임 → ① 쪽 |
| Q3 | 스왑을 **근본 대책**으로 보나, **안전망**으로 보나? | 근본 대책 — 배포 순간만 잠깐 쓰고 평소엔 0이면 충분 → ① 그대로 | 안전망 — 정상 배포는 RAM 안에서 끝나야 함 → ①을 유지하려면 **D2로 메모리를 줄여야 함**, 안 되면 ② |
| Q4 | `deploy.sh` 복잡도를 얼마나 감수할까? | 감수 — 포트 교대·헬스체크·롤백 로직 유지 | 최소화 — 정지 → 기동 → 헬스체크 → 실패 시 이전 jar 재기동 |
| Q5 | 포트폴리오에서 어떤 이야기를 하고 싶나? | "1GB에서 메모리 예산을 실측해 무중단 배포를 유지했다" | "규모를 근거로 다운타임을 허용하고 구조를 단순하게 했다" |

> Q5는 기준이 아니라 결과다. **두 이야기 모두 근거만 있으면 면접에서 설득력이 있다.** 면접관이 보는 건 "무중단을 했냐"가 아니라 "트레이드오프를 숫자로 따졌냐"다.

# 4. 선택지와 추천

## D1. 배포 방식

| | ① 스왑 + 무중단 유지 (현재) | ② 정지 후 기동 |
| --- | --- | --- |
| 다운타임 | 0 (단, 배포 중 응답 지연 가능 → M5) | 단독 기동 시간만큼 (M3, 2분보다 짧을 것으로 예상 — 2분은 JVM 2개가 CPU·메모리를 나눠 쓸 때 수치) |
| 메모리 | 순간 JVM 2개 → RAM 초과분은 스왑 | 항상 JVM 1개 → 여유 |
| 배포 시간 | 약 2분 (두 JVM이 1/8 OCPU를 나눠 씀) | 더 짧을 것으로 예상 |
| 실패 시 | 예전 버전이 아직 떠 있음 → **새 버전만 종료하면 자동 롤백** | 예전 버전이 이미 내려감 → `versions/`의 이전 jar로 재기동해야 함, **그동안 다운타임이 한 번 더** |
| 위험 | 배포 중 예전 버전이 스왑으로 밀려 느려짐. 앱이 커지면(의존성·캐시 추가) 다시 한계 | 배포마다 접속 불가 구간. 기동 실패 시 다운타임 길어짐 |
| 작업량 | 거의 없음 (현재 구조 유지, 실패 처리만 보강) | `deploy.sh` 재작성 (오히려 단순해짐) |
| 근거 | 스왑 환경에서 2회 성공 (단, 2회뿐) | 10/15 복구 때 단독 기동은 정상 |

검토 후 제외: **배포 전 남은 메모리를 보고 ①/② 중 자동 선택** — 두 방식을 모두 유지해야 해서 Q4 기준으로 과함.

**추천 (검토 의견): ①을 유지하되, M5에서 배포 중 응답 지연이 크면(예: 수 초 이상이 반복) ②로 전환.**
- 이유: 이미 2회 성공했고, 실패 시 예전 버전이 남아 있어 롤백이 공짜다. 4주차 피드백 반영으로 배포가 잦아지면(Q2) 다운타임 없는 쪽이 유리하다
- 단, 이 추천은 **Q3를 "근본 대책"으로 본다는 전제**다. "안전망"으로 본다면 D2 결과에 따라 ②가 맞을 수 있다

## D2. JVM 메모리 옵션 조정 (D1과 함께 쓰는 보조 수단)

D1과 따로 고르는 게 아니라 **①을 유지할 때 여유를 만드는 수단**이다. ②를 고르면 우선순위가 낮아진다.

| 후보 | 효과 | 위험 | 근거 측정 |
| --- | --- | --- | --- |
| `server.tomcat.threads.max` 200 → 20~50 | 스레드 스택(스레드당 약 1MB) 상한 축소 | 동시 요청이 몰리면 대기 — 지인 모임 규모에선 영향 미미 | M6 Thread 영역 |
| `-Xss512k` | 스레드당 스택 절반 | 깊은 재귀에서 `StackOverflowError` (현재 코드엔 없음) | M6 |
| `-XX:MaxMetaspaceSize=128m` | Metaspace 상한 | 너무 낮으면 `OutOfMemoryError: Metaspace`로 기동 실패 → 실측값 + 여유로 설정 | M6 Class 영역 |
| `-XX:TieredStopAtLevel=1` | JIT를 C1까지만 → **기동 시간 단축**, 코드 캐시 감소 | 장기 처리량 감소 — 이 규모에선 체감 어려움 | M3 전후 비교 |
| `-Xmx384m` 하향 | 힙 축소 | 랭킹 배치(새벽 4시) 등에서 힙 부족 가능 → 힙 사용량 확인 후에만 | `jstat -gc <pid>` |
| `-XX:+UseSerialGC` | G1보다 메모리 부담 적음 | 없음 | M7 — 이미 SerialGC면 불필요 |

**추천 (검토 의견): M6 실측 후 효과 큰 1~2개만 적용.** 후보를 한꺼번에 넣으면 어느 옵션이 효과가 있었는지 설명할 수 없다(면접 근거 측면에서도 손해). 측정 없이 넣는다면 위험이 가장 적은 `server.tomcat.threads.max` 하향 정도.

## D3. 배포 실패 시 동작

| 선택지 | 내용 |
| --- | --- |
| a. 감지만 | 실패하면 `exit 1` → Actions 실패 표시. 복구는 사람이 |
| b. 감지 + 자동 롤백 | ①: 새 버전 종료·예전 버전 유지 후 `exit 1` / ②: 이전 jar로 재기동 후 `exit 1` |

**추천 (검토 의견): b.** ①에서는 "새 버전 종료"만 하면 되므로 비용이 거의 없다. ②라면 롤백 로직이 늘어나니 a로 시작해도 무방하다.

# 5. 그 외 (선택지 없음)

- **`deploy.sh` 실패 시 `exit 1`** — 헬스체크 실패·기동 실패 경로에서 0이 아닌 값으로 끝나게 한다. Actions의 `ssh-action` 스크립트가 `/bin/bash /home/ubuntu/deploy.sh` 한 줄이므로 그 종료 코드가 그대로 step 결과가 된다. 스크립트 앞에 `set -euo pipefail` 적용 여부는 M1 내용을 보고 판단 (중간 명령의 의도된 실패까지 중단시킬 수 있음)
- **Actions 마지막 단계에 외부 경로 헬스체크** — `curl -f --retry 5 --retry-delay 10 https://booktalker.co.kr/<api 경로>/actuator/health`. 서버 안 `localhost` 확인으로는 10/15 장애 ②(ufw)를 잡지 못했다. Nginx가 actuator 경로를 프록시하는지는 Nginx 설정 확인 필요
- **`deploy.sh`를 저장소에 포함** (예: `book_talker_backend/deploy/deploy.sh`) — 지금은 서버에만 있어 변경 이력·리뷰가 없다. Flyway 도입 이유(변경을 파일로 남기고 리뷰)와 같은 맥락. Actions에서 SCP로 함께 보내거나, 서버 파일을 저장소 사본과 수동으로 맞추는 방식 중 선택 → 단순하게 **우선 저장소에 사본만 두고 서버엔 수동 반영**으로 시작해도 충분

**해석**
- 추정치(프로세스당 550~650MB)보다 실측이 훨씬 작다 (약 335MB)
- 무중단 기동(80초)이 단독 기동(76~87초)과 거의 같다 → 스왑이 있는 지금 **JVM 2개 동시 기동이 기동 속도를 떨어뜨리지 않는다**
- 장애 문서의 "기동 2분 15초", 10/20의 "2분 5초"는 JVM 기동 시간이 아니라 **`deploy.sh`가 기다린 시간**(`sleep 90` + 헬스체크 3회)이다. 실제 기동은 80초대
- M4 (`vmstat 5`, 배포 시작 전부터 측정) 흐름:
  - 0~65초 (새 JVM 기동): 남는 RAM(`free`) 187MB → 9MB. 스왑은 안 쓰고 **파일 캐시를 비워서** 버팀
  - 65~85초 (기동 막바지): 스왑 46MB → 109MB (`so` 최대 5.8MB/s). JVM 2개가 동시에 가장 큰 시점 — **이때 밀려나는 건 아직 서비스 중인 예전 버전의 페이지일 수 있음** → 응답 지연 여부는 M5로 확인
  - 85~100초 (전환·예전 버전 종료): 종료 처리 중 스왑에서 다시 읽음(`si` 최대 1.9MB/s, Nginx 전환 후라 사용자 영향 없음) → 종료 후 스왑 43MB, `free` 251MB로 복귀
- CPU `st`(steal) 70~75%가 기동 내내 지속 — 가상머신이 쓰려던 CPU를 OCI가 내주지 않은 비율(1/8 OCPU 한도). **기동이 느린 원인은 메모리가 아니라 CPU** → D2에서는 메모리 축소 옵션보다 `-XX:TieredStopAtLevel=1`(JIT 부담 감소)이 기동 시간 단축 후보
- 참고: 10/15 `Started` 기록 중 16:39(94초)는 장애 당시 무중단 기동(스왑 없음), 16:53(189초)은 복구 중 기록으로 당시 상황은 미확인 — 단독 기동 값에서는 제외함

# 8. 범위 밖 발견 (이 설계와 별개)

- **공개 저장소에 운영 비밀값이 커밋되어 있음** — `application-prod.yml`에 운영 DB 접속 정보(공인 IP·계정·비밀번호)와 네이버 OAuth `client-secret`이 그대로 있다. 저장소가 PUBLIC이라 누구나 볼 수 있다. 알라딘 키처럼 환경변수로 분리하고, **이미 노출된 값은 교체(DB 비밀번호 변경, 네이버 secret 재발급)** 해야 한다. 히스토리에 남아 있어서 파일 수정만으로는 해결되지 않는다. DB 서버 5432가 외부에 열려 있다면 WAS 서버 IP만 허용하도록 제한하는 것도 함께 검토
- Actions가 `./gradlew build -x test`로 **테스트를 건너뛰고 배포**함 — 지원 이후 과제로 기록만
