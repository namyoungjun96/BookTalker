# 2. 장애 ① — 무중단 배포가 1GB 서버에서 메모리를 넘김

## 무슨 일이 있었나

`deploy.sh`는 무중단 배포를 위해 **예전 버전(8010)을 살려둔 채 새 버전(8011)을 하나 더 띄우고**, 헬스체크 후 전환하는 구조다. 1GB 서버에서 JVM 두 개가 동시에 뜨면서 메모리와 CPU가 포화됐다.

## 왜 `-Xmx384m`으로 막히지 않았나

`-Xmx`는 **힙만** 제한한다. JVM 프로세스 전체 메모리는 그보다 크다.

```
프로세스 메모리 ≈ 힙(최대 384MB) + Metaspace + 스레드 스택(톰캣 스레드 수 × 약 1MB)
               + 코드 캐시 + 다이렉트 버퍼 등
```

추정치로 프로세스당 550~650MB → 두 개면 1GB 서버 RAM(실측 952MiB)을 넘는다. 스왑도 없어서 피할 곳이 없었다.

> 처음 추정은 프로세스당 550~650MB였으나, 10/22 실측 결과 JVM 1개는 약 335MB(RAM 238MB + 스왑 97MB)였다 — `[design]_배포 구조 결정.md` 7장

## 근거

- 기동 시간 **2분 15초** — 평소보다 확연히 느림
- `vmstat` 첫 줄(부팅 이후 평균)에 **`st` 11~13**(하이퍼바이저가 CPU를 회수 — OCI 버스트 제한), **`so` 28~35**(스왑으로 메모리를 내보냄)가 남아 있음. 평상시 측정에서는 둘 다 0
- 새 버전은 사라지고 예전 버전만 남음

> 미확인: OOM killer가 실제로 새 버전을 종료했는지는 `dmesg`/`journalctl -k`로 확인하지 못했다.

## 장애를 늦게 알아챈 이유

`deploy.sh`가 헬스체크 실패 후에도 **종료 코드 0으로 끝나서** GitHub Actions가 success로 표시됐다. 배포 실패를 사람이 로그를 열어봐야만 알 수 있었다.

## 조치

- 스왑 파일 2GB 추가 (`/swapfile`, `/etc/fstab` 등록, `vm.swappiness=10`) — 배포 순간처럼 **잠깐 메모리가 몰릴 때 프로세스가 죽지 않게** 하는 완충재. 평소 스왑 사용량은 0이어야 정상
- 예전 버전 종료 후 새 버전을 8010에 단독 기동

# 3. 장애 ② — 서버 안에서는 정상인데 밖에서 요청이 안 감

## 증상

새 버전이 정상 기동된 뒤에도 브라우저에서 API 요청이 **약 19초 후 실패**하고 로그인 화면조차 띄우지 못했다. FE 화면은 떴기 때문에 처음에는 "백엔드 응답이 느리다"로 보였다.

## 진단 과정 — 안쪽에서 바깥쪽으로

| 단계 | 확인 | 결과 | 판단 |
| --- | --- | --- | --- |
| 1. 서버 자원 | `vmstat 2 5` | CPU 유휴 99%, 스왑 입출력 0, `st` 0 | 서버 과부하 아님 |
| 2. 앱 (DB 미경유) | `curl localhost:8010/actuator` | 302, **0.024초** | 앱 정상 |
| 3. 앱 + DB | `curl localhost:8010/actuator/health` 5회 | `UP`, 0.1~0.5초 (첫 회 1.1초) | DB 연결 정상. 19초의 원인 아님 |
| 4. 외부 → 서버 | Postman, PowerShell `Invoke-WebRequest https://booktalker.co.kr` | **연결 자체가 안 됨** | 서버 바깥과 안 사이 어딘가에서 끊김 |
| 5. 실제 요청 경로 | 요청 URL 확인 | `IP:8010`이 아니라 **`https://booktalker.co.kr`(443) → Nginx → 8010** | 확인 대상이 8010이 아니라 443 |
| 6. Nginx | `ss -ltnp \| grep -E ':80 \|:443 '` | `0.0.0.0:443`, `0.0.0.0:80` LISTEN | Nginx 정상 |
| 7. 호스트 방화벽 | `iptables -L INPUT`, `ufw status` | ufw **active**, 기본 정책 DROP, 허용은 **22·8010뿐** | **원인 확정 — 443이 Nginx에 닿기 전에 버려짐** |

```
[브라우저] ──https──▶ booktalker.co.kr:443
                         │
                   ┌─────▼──────── WAS 서버 ──────────────┐
                   │  ufw: 22, 8010만 허용  ← 여기서 차단   │
                   │        │                             │
                   │  Nginx :80/:443 (정상 대기)           │
                   │        │ localhost 프록시              │
                   │  Spring Boot :8010 (정상)             │
                   └──────────────────────────────────────┘
```

## 왜 헷갈렸나

- **서버 안에서 하는 모든 확인이 정상이었다.** 앱, DB, Nginx 모두 살아 있었고, 막힌 건 바깥에서 들어오는 입구 하나였다
- **FE 화면은 떴다.** PWA 캐시가 서버 없이 화면을 보여준 것으로 추정 → "백엔드만 느리다"로 오해
- **프로젝트 문서의 아키텍처가 실제와 달랐다.** CLAUDE.md에는 "브라우저 → WAS:8010 직접 요청"으로 적혀 있어 8010만 확인하게 됐다. 실제로는 도메인 + Nginx(443) 경유
- **에러 알림이 없었다.** Discord Webhook은 애플리케이션 ERROR 로그만 보낸다. 요청이 앱까지 오지 않으니 에러도 없었다

## 조치

```bash
ufw allow 80/tcp
ufw allow 443/tcp
```

ufw 규칙은 자동 저장되어 재부팅 후에도 유지된다.

## 미확인

- **ufw가 언제, 왜 켜졌는지.** 이전에는 iptables에 8010 규칙을 직접 넣어 운영했다(같은 규칙이 2개 중복 존재). 재부팅 시 ufw가 활성 상태로 올라오며 80/443을 막은 것으로 추정
  - 확인: `grep ENABLED /etc/ufw/ufw.conf`, `journalctl -u ufw`, `last reboot`, `grep -i ufw /var/log/syslog`

# 4. 배운 점

| 교훈 | 내용 |
| --- | --- |
| **무중단 배포는 공짜가 아니다** | 순간적으로 자원이 2배 필요하다. 1GB 환경에서는 스왑 같은 완충재나 다운타임 허용 방식과의 트레이드오프를 따져야 한다 |
| **`-Xmx` ≠ 프로세스 메모리** | 힙 외 영역(Metaspace, 스레드 스택 등)까지 계산해야 컨테이너·소형 VM에서 메모리 예산을 세울 수 있다 |
| **배포 성공 = 실제 경로로 요청이 성공** | 서버 안 `localhost` 헬스체크는 방화벽·Nginx·DNS를 검증하지 못한다. 사용자와 같은 경로(도메인 + HTTPS)로 확인해야 한다 |
| **계층별 분리 진단** | 자원 → 앱 → DB → 포트 LISTEN → 호스트 방화벽 → 클라우드 보안 목록 → DNS. "어디까지 되는가"를 좁히면 원인이 하나로 수렴한다 |
| **문서와 실제 구조의 불일치도 장애 요인** | 잘못된 아키텍처 문서가 진단 범위를 잘못 잡게 만들었다 |
| **실패는 시끄러워야 한다** | 실패해도 0으로 끝나는 스크립트, 앱 에러만 보는 알림은 "조용한 실패"를 만든다 |
