# [design] 운영 DB 마이그레이션 (팀 기능 1차 배포)

2026년 10월 14일 · `feat/team-domain` → main 머지(= 백엔드 자동 배포) 전에 운영 DB에 적용할 스키마 변경 정리

> 설계 검토에 AI(Claude)를 활용했고, 선택·결정과 백엔드 구현은 직접 했습니다.

**상태: 적용 완료 (2026-10-15, 1차 배포 전 운영 DB에 수동 적용) — 이후 스키마 변경은 Flyway로 이관 (`[design]_Flyway 도입.md`)**

- 관련: `docs/decision/10월 로드맵.md` 3주차, CLAUDE.md "운영 DB 마이그레이션: `review.is_public` → `visibility`"
- SQL은 개발자가 운영 DB에 직접 실행한다. 아래 SQL은 **초안** — 4장의 방법으로 Hibernate 생성 DDL과 대조한 뒤 확정

---

# 1. 왜 직접 해야 하나

| 이유 | 내용 |
| --- | --- |
| **main 머지 = 자동 배포** | `.github/workflows/gradle.yml`이 main push 시 빌드 → 운영 서버 전송 → `deploy.sh` 실행 |
| **운영을 `ddl-auto: validate`로 전환** (함께 커밋 예정) | `validate`는 아무것도 만들지 않고 검사만 함. 테이블이 하나라도 없으면 **앱 기동 실패** → 이번 배포에 필요한 스키마를 전부 미리 만들어야 함 |
| `update`로 두더라도 안 되는 것 | ① `visibility` NOT NULL 컬럼 추가가 기존 행 때문에 실패(앱은 뜬 채 리뷰 API 500) ② `oauth2_user.provider_id` UNIQUE가 만들어지지 않음 (2-2) |

`validate`가 검사하는 것: 테이블·컬럼 존재, 컬럼 타입. **검사하지 않는 것**: UNIQUE, FK, NOT NULL, CHECK. → 제약을 빠뜨려도 기동은 되지만 조용히 무결성이 빠진다. 4장 체크리스트로 따로 확인.

# 2. 변경 내용

## 2-1. `review` — `is_public` → `visibility`

| 결정 | 이유 |
| --- | --- |
| `visibility`에 **`DEFAULT 'PRIVATE'`** | red-green 전환 중 예전 버전(visibility를 모름)이 리뷰를 써도 NOT NULL에 막히지 않음. 롤백 시에도 동작 |
| 기존 값 변환: `is_public = true` → `PUBLIC`, 그 외(false·NULL) → `PRIVATE` | 기존 정책에서 NULL은 비공개(기본 false) |
| **`is_public`은 지우지 않고 NOT NULL만 해제** | 새 코드는 값을 넣지 않으므로 NOT NULL이면 INSERT 실패. 안정화 후 별도로 삭제(롤백 여지 확보). `validate`는 엔티티에 없는 컬럼이 남아 있어도 통과 |

## 2-2. `oauth2_user.provider_id` UNIQUE

- `team_member.provider_id`가 이 컬럼을 FK로 참조 → 참조 대상은 PK 또는 UNIQUE여야 함
- 엔티티에 `@Column(unique = true)`를 붙였지만(7월 `f3a986e`), **`ddl-auto: update`는 이미 있는 컬럼에 UNIQUE를 추가하지 않음**(Hibernate 6에서 컬럼의 unique는 테이블 생성·컬럼 추가 시에만 반영). 로컬 기동 로그에 UNIQUE DDL은 없고 FK 생성 실패만 반복됨(10/14 확인, 13회)
- 중복 데이터 때문이 아님 — 운영에서 중복 조회 결과 없음(10/14 개발자 확인). 그래도 적용 직전 다시 확인
- 로컬에서 겪은 FK 에러는 두 단계였음 (10/14 해결)
  1. UNIQUE가 없어서 FK 생성 불가 (`there is no unique constraint matching given keys`) → UNIQUE 수동 추가
  2. 다시 기동하자 FK 생성 시 기존 행 검사에서 실패 (`violates foreign key constraint ... Key (provider_id)=(:u1) is not present`) → `oauth2_user`에 없는 사용자를 가리키는 테스트 찌꺼기 행 삭제 후 FK 정상 생성. 문구는 "insert or update"지만 FK 추가 시 기존 데이터 검사 실패도 같은 문구
  - 운영에는 `team_member`가 아직 없어 2번 상황은 생길 수 없음. 대신 **로컬 DB는 리허설 기준으로 쓰지 않는다** → 4-3처럼 운영 덤프를 복원해서 리허설

## 2-3. `team`, `team_member` 신규 생성

엔티티 기준 컬럼 (Spring 기본 네이밍: camelCase → snake_case)

| 테이블 | 컬럼 | 제약 |
| --- | --- | --- |
| `team` | `team_id` bigint identity, `team_name`, `team_description`, `created_at`, `updated_at`, `code` varchar(13) | PK, `code` UNIQUE·NOT NULL |
| `team_member` | `team_member_id` bigint identity, `team_id`, `provider_id`, `role`, `status`, `display_name`, `joined_at` | PK, `(provider_id, team_id)` UNIQUE, `team_id` → `team` FK, `provider_id` → `oauth2_user(provider_id)` FK, `provider_id`·`role`·`status` NOT NULL |

- 초대코드 컬럼 이름은 **`code`** (엔티티 필드 `Team.code`). 스펙 정의서 데이터 모델 표의 `invite_code`는 실제와 다름 → 문서 정리 시 수정
- enum(`role`, `status`)은 PostgreSQL enum이 아닌 varchar + CHECK (Hibernate 6 기본, `10/2 FIX` 커밋으로 pg enum 미사용 결정)
- 모임 삭제 시 모임원 삭제는 JPA cascade(`orphanRemoval`)가 처리 → FK에 `ON DELETE CASCADE`는 두지 않음

# 3. SQL 초안

PostgreSQL은 DDL도 트랜잭션으로 묶을 수 있어서, **중간에 하나라도 실패하면 전부 되돌아간다.**

```sql
BEGIN;

-- 2-1. review
ALTER TABLE review ADD COLUMN visibility varchar(255) DEFAULT 'PRIVATE';
UPDATE review SET visibility = CASE WHEN is_public = true THEN 'PUBLIC' ELSE 'PRIVATE' END;
ALTER TABLE review ALTER COLUMN visibility SET NOT NULL;
ALTER TABLE review ADD CONSTRAINT review_visibility_check
    CHECK (visibility IN ('PUBLIC', 'GROUP', 'PRIVATE'));
ALTER TABLE review ALTER COLUMN is_public DROP NOT NULL;   -- 이미 nullable이면 아무 일도 안 함

-- 2-2. oauth2_user
ALTER TABLE oauth2_user ADD CONSTRAINT uk_oauth2_user_provider_id UNIQUE (provider_id);

-- 2-3. team
CREATE TABLE team (
    team_id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_name        varchar(255),
    team_description varchar(255),
    created_at       timestamp(6),
    updated_at       timestamp(6),
    code             varchar(13) NOT NULL,
    CONSTRAINT uk_team_code UNIQUE (code)
);

-- 2-3. team_member
CREATE TABLE team_member (
    team_member_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_id        bigint,
    provider_id    varchar(255) NOT NULL,
    role           varchar(255) NOT NULL CHECK (role IN ('OWNER', 'MEMBER')),
    status         varchar(255) NOT NULL CHECK (status IN ('ACTIVE', 'PENDING', 'BANNED', 'INACTIVE')),
    display_name   varchar(255),
    joined_at      timestamp(6),
    CONSTRAINT uk_team_member_provider_id_team_id UNIQUE (provider_id, team_id),
    CONSTRAINT fk_team_member_team FOREIGN KEY (team_id) REFERENCES team (team_id),
    CONSTRAINT fk_team_member_oauth2_user FOREIGN KEY (provider_id) REFERENCES oauth2_user (provider_id)
);

COMMIT;
```

> 열 타입·길이는 Hibernate 6 + PostgreSQL 기본값을 가정한 것이라 4장의 생성 스크립트와 반드시 대조. enum CHECK 값은 코드와 일치 확인(10/14: `MemberRoleEnum` OWNER·MEMBER, `MemberStatusEnum` PENDING·ACTIVE·BANNED·INACTIVE). enum 값을 추가하면 CHECK도 같이 바꿔야 함.

# 4. 확정 전 준비

## 4-1. 운영 DB에서 확인 (개발자 직접)

| # | 확인 | 쿼리 |
| --- | --- | --- |
| 1 | `provider_id` 중복 없음 | `SELECT provider_id, COUNT(*) FROM oauth2_user GROUP BY provider_id HAVING COUNT(*) > 1;` |
| 2 | `review.is_public` 정의(NOT NULL·기본값), `review` 행 수 | `\d review` / `SELECT COUNT(*) FROM review;` |
| 3 | `is_public` 값 분포 (NULL 포함) | `SELECT is_public, COUNT(*) FROM review GROUP BY is_public;` |
| 4 | `team`, `team_member` 테이블이 아직 없음 | `\dt` |

## 4-2. Hibernate가 만들 DDL 뽑아서 대조 (추천)

손으로 쓴 SQL은 타입·제약을 빠뜨리기 쉬우므로, 로컬에서 Hibernate가 **처음부터 만들 경우의 DDL**을 파일로 뽑아 3장과 비교한다. 로컬 DB는 같은 버그(2-2) 때문에 FK가 빠져 있어서 `pg_dump`로 뜨는 것보다 정확함.

```yaml
# 로컬에서 한 번만 임시로 추가 (커밋하지 않음)
spring:
  jpa:
    properties:
      jakarta.persistence.schema-generation.scripts.action: create
      jakarta.persistence.schema-generation.scripts.create-target: build/create.sql
```

→ 기동 후 `build/create.sql`에서 `team`, `team_member`, `review`, `oauth2_user` 부분을 3장과 비교.

## 4-3. 로컬 리허설

1. 운영 DB를 덤프해서 로컬에 복원 (`pg_dump` → `pg_restore`/`psql`)
2. 3장 SQL 실행
3. 백엔드를 **`validate`로** 로컬 기동 → 기동 성공 확인
4. 스모크 테스트: 기존 리뷰 목록·상세(공개 범위 표시 확인), 리뷰 작성, 랭킹, 모임 생성 → 초대 → 가입
5. 제약 확인: `SELECT conrelid::regclass, conname, contype FROM pg_constraint WHERE conrelid::regclass::text IN ('oauth2_user','team','team_member','review');`

# 5. 배포 순서

| # | 단계 | 비고 |
| --- | --- | --- |
| 1 | 4-1 확인, 4-2 대조, 4-3 리허설 | |
| 2 | `application-prod.yml` `ddl-auto: validate` 커밋 | 같은 PR에 포함 |
| 3 | PR 문서(`[commit]`) → PR 생성 | |
| 4 | **운영 DB에 3장 SQL 실행** | 예전 버전(main)은 새 스키마에서도 동작 — `visibility` 기본값, `is_public` 유지, 새 테이블은 안 씀 |
| 5 | 머지 → 자동 배포(red-green) | 새 버전이 `validate`로 기동 실패하면 전환되지 않음 → 로그 확인 |
| 6 | **바로 FE 배포** (수동) | 새 BE + 예전 FE 사이에는 리뷰 작성 불가(예전 FE는 `isPublic` 전송 → 400). 사용자가 없어 영향은 작음 |
| 7 | 접속 확인 | 리뷰 목록·작성, 모임 생성·초대 링크(새로고침 포함 — Nginx `try_files`) |

- 4와 5 사이에 예전 버전으로 공개 리뷰가 작성되면 `visibility`가 기본값 `PRIVATE`로 들어간다. 머지 직전에 2-1의 `UPDATE`를 한 번 더 돌리면 맞춰짐 (사용자가 없으면 생략 가능)
